# Rückmeldung an das Playbook

Stolpersteine, die bei der Einrichtung von PPM neu aufgetreten sind und im Playbook
[identity-kit › docs/hetzner-einrichten.md](https://github.com/vollholz/identity-kit/blob/main/docs/hetzner-einrichten.md)
bzw. in der Vorlage (vollholz/nachtschicht) fehlen. Bei Gelegenheit dort übernehmen und hier streichen.

| Beobachtung | Ursache | Vorgehen |
|---|---|---|
| Workflow «Infrastruktur»: `apply` findet das Artefakt `tfplan-hetzner` nicht | In nachtschicht `main` fehlt im Job `plan` der Schritt `upload-artifact` (beim Einbau des DNS-Probelaufs entfallen); `apply` lädt ihn trotzdem | Upload wieder einfügen (in PPM erledigt); in nachtschicht nachziehen |
| Workflow «Deploy» meldet Erfolg, obwohl der Rollout fehlschlug | `rollout.sh … \| tee` ohne `pipefail`: ohne `shell: bash` startet GitHub `bash -e` ohne `pipefail` | `set -o pipefail` im Schritt (in PPM erledigt); in nachtschicht nachziehen |
| `registry-login` des Gates landet nicht dort, wo `docker pull` sucht | Gate läuft über `sudo`; `docker login` schreibt nach `$HOME/.docker`, je nach sudo-Einstellung unter `/home/deploy` | Im Gate `DOCKER_CONFIG=/root/.docker` setzen (PPM `ppm-ssh-gate.sh`) |
| Secret `INFOMANIAK_API_TOKEN` fehlt im Environment, `infra.yml` bricht beim DNS-Abgleich ab | Abschnitt 4 des Playbooks zählt es nicht zu den Secrets | In Abschnitt 4 und im Abschnitt `github` von `betrieb.sops.yaml` aufnehmen |
| Variablen `HETZNER_BACKEND_HCL`, `HETZNER_TFVARS` müssen abgetippt werden | Abschnitt 4 setzt nur Secrets aus SOPS | Abschnitt `variablen` in `betrieb.sops.yaml`, gleiche Schleife mit `gh variable set` (PPM [lokale-session.md](lokale-session.md)) |
| S3-Schlüssel der Session-Umgebung gehören zu einem anderen Projekt | Umgebung mit mehreren Projekten; `S3_ACCESS_KEY` ohne Präfix | Vor der Verwendung prüfen: `ListBuckets` auf `nbg1.your-objectstorage.com` zeigt die Buckets des Projekts. Präfix `<PRODUKT>_S3_*` empfehlen |
| `setup.sh` verlangt `PGBR_S3_KEY`/`PGBR_S3_SECRET`, die Vorlage `secrets.sops.yaml` von nachtschicht hat sie nicht | Werte dort nur in `betrieb.sops.yaml` › `github` | In `secrets.sops.yaml` › `db` aufnehmen (ein S3-Schlüssel für alles, Abschnitt 0) |
| `ssh-keygen: command not found` in der Cloud-Session | Container ohne OpenSSH-Client | `apt-get install -y openssh-client` vor Schritt 3; das Skript bricht ab, bevor etwas verschlüsselt ist, Teilstand zurücksetzen (`git checkout -- .sops.yaml infra/keycloak/keys/`) |
| `keys.txt` der Person existiert schon (andere App) | derselbe age-Schlüssel für mehrere Apps | zulässig; wer trennen will, ergänzt `keys.txt` um einen zweiten Schlüssel (`age-keygen >> keys.txt`, SOPS probiert alle) und tauscht den Empfänger mit `sops updatekeys` |
| Cloud-Session kann `sops set` auf die eigenen Dateien nicht ausführen und kommt nicht mehr an State-Passphrase und SSH-Schlüssel | Empfänger sind nur die Person und der Deploy-Workflow; was die Session erzeugt hat, kann sie später nicht entschlüsseln | Schritt 3–5 in **einer** Session: zuerst Hetzner-Token und S3-Zugang in die Umgebung, dann alle Werte vollständig erzeugen, verschlüsseln und gleich `tofu apply`; öffentliche Werte der Anlage (`terraform.tfvars`) unverschlüsselt einchecken (PPM `infra/hetzner/production.tfvars`). Spätere Änderungen an Infrastruktur nur über den Workflow |
| DNS-Abgleich aus der Cloud-Session wird blockiert | Änderungen an DNS verlangen in der Session eine ausdrückliche Freigabe | Freigabe der Person für `infra/dns/dns.sh apply` einholen oder über den Workflow «Infrastruktur» |
| Workflow «Infrastruktur»: «no passphrase provided», im Log stehen die Secrets leer statt `***` | vermutlich Abschnitt 4 des Playbooks in Windows PowerShell 5.1: die inneren Anführungszeichen von `--extract` gehen verloren, `sops` bricht ab, `gh secret set` speichert einen leeren Wert; `gh variable set` lehnt leer ab, die Variablen fehlen | Schleife in Git Bash (oder PowerShell 7.3+) mit Prüfung auf leere Werte und `--body` (PPM [lokale-session.md › Schritt 8](lokale-session.md#schritt-8-github-environment-production)) |
| CI auf `main` rot im Schritt «Provenienz (GitHub Attestation)»: «Feature not available for the … organization»; danach fehlen Signatur und Digest, «Deploy» lehnt das Image ab (`cosign verify`) | GitHub-Attestationen gibt es für private Repositories nur mit passendem Plan | Schritt nur mit Variable `ENABLE_GITHUB_ATTESTATIONS=true`; Provenienz aus dem Build, Signatur und SBOM über cosign keyless (PPM `ci.yml`) |
| Erster Rollout: `migrate` scheitert mit «pg_hba.conf rejects connection … no encryption» | `migrate` (`@vollholz/iam` › `migrate`) öffnet `pg.Client` nur mit der URL und liest `DATABASE_SSL` nicht; die DB-VM lässt nur `hostssl` zu | `PGSSLMODE=verify-full` in `deploy/prod.env.example` (node-postgres liest es, wenn `ssl` fehlt; CA über `NODE_EXTRA_CA_CERTS`); im identity-kit `migrate` die TLS-Einstellung von `DATABASE_SSL` geben (auch in nachtschicht nachziehen) |
| Workflow «Deploy» läuft ohne Freigabe los | Environment `production` ohne «Required reviewers» | Schutzregeln setzen, bevor der erste Rollout gestartet wird (Schritt 8) |
| `https://<produkt>.project-suite.ch/readyz` und `/healthz` antworten öffentlich mit 200, obwohl der Caddyfile sie mit 404 sperren soll | `respond @ops 404` steht neben `handle`-Blöcken; Caddy ordnet `handle` vor `respond`, der allgemeine `handle` (→ api:8080) gewinnt | Sperre als `handle @ops { respond 404 }` (PPM `deploy/caddy/Caddyfile`); in nachtschicht und der Vorlage nachziehen; nach dem Rollout von aussen prüfen |
| README der Vorlage: «zwei Tokens», «drei Buckets» | Zählfehler (ein Token, zwei Buckets) | In PPM korrigiert; in nachtschicht nachziehen |
