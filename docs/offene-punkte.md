# Offene Punkte

Offene Punkte der Technik und des Betriebs. Fachliche Fragen stehen im [Masterdokument](PPM-Master.md#12-offene-punkte),
in der [Klärungsliste](anhang/klaerungsliste.md) (K01–K25) und für die Oberfläche im [Fahrplan](ux/fahrplan.md#offene-fragen)
(UX-OF-1–18). Stand: Initialisierung der App (Oktober 2026). Verantwortung: **Team** (Entwicklung PPM), **Betrieb**
(Infrastruktur, Keycloak-Instanz), **identity-kit** (Baukasten), **CSP** (Auftrag und Kunde).

| Nr. | Thema | Beschreibung | Vorschlag | Verantwortung |
|---|---|---|---|---|
| <a id="op-01"></a>OP-01 | Betriebsort | Wo PPM betrieben wird, ist nicht entschieden (Kundenmaterial Q6–Q8 ist intern klassifiziert). `deploy/hetzner/`, `infra/hetzner/`, `deploy/k8s/` und die Workflows `deploy.yml`, `infra.yml` sind die Vorlage des Gerüsts, nicht eingerichtet. | Betriebsort und Datenhaltung mit CSP und der Insel Gruppe klären; danach die passende Vorlage einrichten, die übrigen entfernen | CSP, Betrieb |
| <a id="op-02"></a>OP-02 | Keycloak-Instanz | `https://identity.project-suite.ch` ist angenommen (`identity.app.json`, `deploy/`), nicht bestätigt. | Adresse beim Betreiber bestätigen, sonst Manifest und `prod.env.example` anpassen | Betrieb |
| <a id="op-03"></a>OP-03 | Adresse der App | `https://ppm.project-suite.ch` ist angenommen (`identity.app.json`, `deploy/`, `.github/workflows/deploy.yml`). | Mit OP-01 festlegen | CSP, Betrieb |
| <a id="op-04"></a>OP-04 | Schlüsselpaare der Clients | `infra/keycloak/keys/` fehlt: Die Schlüssel entstehen lokal mit `npx create-iam-app keys` (privat nach `~/.identity/ppm/`), in einer Session gingen die privaten verloren. | Lokal `npx create-iam-app keys`, öffentliche Schlüssel committen, `ppm-tofu.json` an den Betreiber, private als Secrets | Team, Betrieb |
| <a id="op-05"></a>OP-05 | Realm anlegen | Realm `ppm` und `ppm-iac` sind nicht angelegt ([identity-kit.md](identity-kit.md), identity-kit `docs/neue-app.md` Schritt 3). State-Bucket `ppm-tofu-state` in `identity.app.json` ist angenommen. | Nach den Schlüsseln (OP-04) `infra/keycloak/kc.sh bootstrap init && … apply`; Bucket anlegen | Betrieb |
| <a id="op-06"></a>OP-06 | Erste Organisation | `identity.app.json` nennt nur das Konto des Betriebs, keine `organizations`. | Alias, Name und Admin der ersten Organisation (z. B. Insel Gruppe) eintragen, dann `npm run identity:first-org` | CSP |
| <a id="op-07"></a>OP-07 | SOPS | `.sops.yaml` enthält Platzhalter statt age-Empfängern; `deploy/hetzner/secrets.sops.yaml` fehlt (nur `.example`). | Mit OP-01 | Betrieb |
| <a id="op-08"></a>OP-08 | Pakete aus GitHub Packages | `@vollholz/*` liegen auf GitHub Packages von `vollholz`; das Repository liegt bei `CSPAG`. `GITHUB_TOKEN` reicht ausserhalb von `vollholz` meist nicht (403). | Secret `NPM_READ_TOKEN` (classic, nur `read:packages`) im Repository hinterlegen; CI nimmt es zuerst | Team |
| <a id="op-09"></a>OP-09 | Lockfiles | `package-lock.json` (beide) enthält für `@vollholz/*` kein `resolved`/`integrity` (lokale Registry von identity-kit). | Einmal `npm install` mit Zugang zu GitHub Packages, Lockfiles committen | Team |
| <a id="op-10"></a>OP-10 | Anrede im Baukasten | Die Oberfläche von PPM spricht mit «Sie» (UX-E7); die Seiten und Meldungen von `@vollholz/iam-web` und die Fehlertexte von `@vollholz/iam`/`@vollholz/platform` sind in Du-Form. | Bis zur Klärung von UX-OF-1 so belassen; bleibt es bei «Sie», im identity-kit die Anrede einstellbar machen | identity-kit, CSP |
| <a id="op-11"></a>OP-11 | Rollen und Typen | Das Modell hat Stufe «einfach» mit den Rollen `gl` und `leser`. Projektrollen (PL, CTL, SP, KT), Portfolios und Gremien als Orte fehlen; Sichtbarkeit je Rolle in [ux/informationsarchitektur.md](ux/informationsarchitektur.md). | Mit den Modulen der Etappen E0–E2 als Typen (`projekt`, `portfolio`, `gremium`) einführen | Team |
| <a id="op-12"></a>OP-12 | Nicht ausgeführt | In der Session liefen weder Docker-Build noch Compose-Stack, Keycloak-Setup, E2E-Tests oder Workflows. Geprüft wurden Typen, Modulgrenzen, Backend-Tests mit Datenbank, Webapp-Tests, Build und Konformität (Repository). | Ersten CI-Lauf und lokal `npm run dev:setup` + `npm run e2e` prüfen | Team |
| <a id="op-13"></a>OP-13 | Rauchtest mit Maschinen-Client | `scripts/smoke.ts` braucht einen Maschinen-Client (`SMOKE_CLIENT_ID`, `SMOKE_CLIENT_KEY`) mit Organisation und Scopes. | Über `machine_clients` in `identity.app.json` anlegen | Betrieb |
| <a id="op-14"></a>OP-14 | npm-Version | Mit npm 10.9 bricht `npm install` in `web/` ab (`edgesOut`); mit npm 11 läuft es. | npm ≥ 11 in CI und Doku voraussetzen | Team |
| <a id="op-15"></a>OP-15 | Kubernetes-Platzhalter | `deploy/k8s/`: DB-CIDR, Namespaces und Issuer sind Platzhalter; Secrets je Dienst liefert ein Overlay. | Nur falls OP-01 Kubernetes ergibt | Betrieb |
| <a id="op-16"></a>OP-16 | Organisation löschen | `tenant delete` (`tenantDelete` in `@vollholz/platform`) schaltet in seiner Transaktion `FORCE RLS` und Benutzer-Trigger der Mandantentabellen kurz aus (exklusive Sperren); das Protokoll des Mandanten geht mit ihm, ein Eintrag bleibt im Protokoll der Plattform. | Nur in Wartungsfenstern nutzen; Löschfunktion im Baukasten prüfen | Team, identity-kit |
